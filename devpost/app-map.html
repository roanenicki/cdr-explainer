CDR Explainer: App Map

A take-home guide to how the code fits together: what the main pieces are, what happens when you click a button, and where to start when you want to change something.

The app in one paragraph

You give it a CSV of voice call detail records (an upload, or one of the two sample buttons). It runs 5 deterministic telecom checks, works out the share of valid rows, and shows a colored verdict, metric cards, one card per check with its billing impact, and a filterable table of the rows that failed. Nothing is saved anywhere and no AI or API key is involved.

The main pieces

  • The page: app.pyThe only Streamlit file. It takes the file in, remembers it in st.session_state, and draws the report.
  • The engine: cdr_explainer/Plain Python with no Streamlit. Reads the file, runs the checks, builds the report. That's why pytest can test it directly.
  • The wording and look: explain.py, ui_html.pyEvery sentence a user reads, and the HTML for the banner and cards.
  • The proof: data/ + tests/Synthetic sample files with planted errors, their expected counts, and the tests that compare the two.

Reference route: 3 stops

A reference route to follow when you want to: it wasn't toured live during the build wrap-up. Search for the anchor in your editor (Ctrl+Shift+F in VS Code). Line numbers drift, names don't.

  1. app.py: search def load_sample and def set_source
    The button's on_click callback stores the file's bytes in st.session_state["source"] and resets the filter. Streamlit then reruns the whole file. Near the bottom, analyze(source["data"]) runs and draw_report draws the result. A button is only "clicked" for one rerun, which is why the file lives in session_state and not in the button.
    Show the code 
    def set_source(name: str, data: bytes) -> None:
    """The most recent upload or sample click wins; a new file starts unfiltered."""
    st.session_state["source"] = {"name": name, "data": data}
    st.session_state[FILTER_KEY] = ALL_CHECKS


def load_sample(filename: str) -> None:
    set_source(filename, (DATA / filename).read_bytes())
    st.session_state[UPLOAD_VERSION] = st.session_state.get(UPLOAD_VERSION, 0) + 1
  2. cdr_explainer/report.py: search def analyze
    The engine's front door, in two lines. load_cdrs (loader.py) turns bytes into a table of text, or raises a FileProblem with the message the user sees. run_all (checks.py) runs the 5 checks with their skip rules. build_report computes the score, the status (99 / 90 thresholds) and the anomaly table.
    Show the code 
    def analyze(data: bytes) -> Report:
    """The only function the page needs: file bytes in, report out."""
    df = load_cdrs(data)
    return build_report(df, run_all(df))
  3. cdr_explainer/explain.py: search def verdict_text; then cdr_explainer/ui_html.py: search def verdict_banner
    verdict_text writes "Review before sending: 51 rows have issues." and main_issues writes the "Main issues" line. verdict_banner wraps them in the orange HTML banner, escaping all text. Wording and look are kept apart, so you can change one without touching the other.

A practice to reuse

Write the expected result into the plan, then make a test say it.

The PRD (devpost/prd.md → Health Score and Verdict) set an observable acceptance line before any code existed: "The dirty sample shows 94.9%, orange, 'Review before sending: 51 rows have issues.'" The generator plants exactly those errors and checks that each one trips only its intended check (samples.py → _assert_planted). tests/test_samples.py → test_dirty_sample_headline asserts that exact sentence. Keeping the engine free of Streamlit is what made that test possible without a browser.

On another project (with Kiro or anywhere else): for each requirement, write the result someone could observe, keep the logic that produces it separate from the UI, and turn the observation into a test. A requirement that has a test becomes a check you can rerun at any time.
